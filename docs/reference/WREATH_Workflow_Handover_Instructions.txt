## 2. Read the Governance Sources Before Making Changes

Inspect the repository's applicable:

- `AGENTS.md` and other agent instructions.
- Architecture decision records A–I and relevant sub-decisions.
- Shared-contract and WHIR specifications.
- DSN-001 and DSN-002 tickets and SOPs.
- Migration registry, workflow, prompt library, and verification documents.
- Acceptance matrices, traceability records, and source references.
- Existing approval records and unresolved-decision lists.

Verify that the documents you find are authoritative and current. If a referenced source is absent, record it as missing. Do not invent approvals or infer approval from a recommendation, generated document, successful test, or previous agent response.

- Approved decisions.
- Conditional or partial approvals.
- Proposed decisions.

Do not silently change a decision's status. Record evidence and request owner approval when required.

## 3. Finalize the Workflow Changes

Audit and complete these workflow areas, reusing valid existing work rather than recreating documents unnecessarily.

### A. Migration authorization gate

Define the mandatory prerequisites before implementation begins:

- Relevant architecture and ownership decisions are approved.
- DSN-001 and DSN-002 scope and acceptance criteria are explicit.
- Shared-contract ownership and dependencies are settled sufficiently for the first implementation slice.
- Persistence, versioning, identity, and error-handling decisions required by that slice are resolved.
- Required source evidence and approval records are available.
- Tests, fixtures, acceptance criteria, and verification procedures are defined.
- Deferred and excluded work is documented.

If a prerequisite remains unresolved, identify the exact blocker and its impact. Do not start broad engine migration to work around an unresolved architecture decision.

### B. Decision governance

Make it clear who can propose, review, approve, defer, or reopen decisions. Maintain traceability between the decision, its evidence, its approval, and affected implementation work.

Generated documents and agent recommendations must never become owner approvals automatically.

### C. Acceptance criteria and traceability

Check the acceptance matrix for:

- Stable criterion IDs.
- Links to parent requirements and architecture decisions.
- Explicit verification methods and evidence.
- Clear pass, fail, blocked, and unverified outcomes.
- No accidental deletion, duplication, or double-counting of criteria.
- Consistent status between tickets, SOPs, decision records, and verification documents.

Preserve established IDs unless a documented reason requires a change.

### D. Migration checkpoints

Define checkpoints that separate:

1. Repository and source audit.
2. Architecture and contract approval.
3. Minimal implementation-slice authorization.
4. Implementation.
5. Automated and manual verification.
6. Integration and regression checks.
7. Review, commit, and remote synchronization.
8. Final acceptance and handover.

Each checkpoint must have explicit entry conditions, required evidence, exit conditions, and blocker handling.

### E. Agent and Git workflow

Document safe operating rules:

- Inspect before editing.
- Make focused changes.
- Review diffs before staging.
- Avoid broad staging commands such as `git add .` or `git add -A`.
- Do not overwrite unrelated user changes.
- Do not force-push.
- Do not claim a push succeeded without verifying the remote result.
- Respect the repository's permissions and approval requirements.
- Report commands that failed and checks that were not run.

Agent permission settings are not a security sandbox. Do not rely on them as a substitute for review.

## 4. Preserve the DSN-001 and DSN-002 Boundaries

### DSN-001: Schematic engine

The proposed minimum scope includes a single schematic sheet, symbol instances and pins, wires and junctions, connectivity, persistence, transforms, properties and reference designators, CRUD operations, structured errors, tests, and a documented versioned API contract.

The API-facing boundary should eventually support both UI/human callers and automation clients. This does not automatically require a separately deployed microservice or a complete UI.

Do not silently include ERC, PCB placement/routing, AI/RL, or full KiCad compatibility in the minimum version.

### DSN-002: Component and library engine

The proposed scope includes reusable component metadata, symbol definitions and pins, footprints and pads, library identity/versioning, associations, pin-to-pad mapping, deterministic lookup, validation, persistence, and a documented API contract.

It does not own placed schematic instances, schematic connectivity, PCB placement/routing, ERC, or DRC.

### Shared contract

Verify the actual approved source before freezing the shared interface. Neither engine should acquire an accidental dependency on the other engine's concrete implementation if the approved architecture specifies a shared-contract boundary.

These are scope summaries, not evidence that the tickets or architecture decisions have received final approval. Verify the actual approval records.

## 5. Validate the Result

After editing:

- Review every changed file and the complete Git diff.
- Check Markdown links and referenced file paths.
- Check consistency of decision statuses and requirement IDs.
- Run relevant repository-defined documentation checks and tests.
- Record every command that failed, every test not run, and every unverifiable claim.
- Confirm no unrelated source code, configuration, or user work was changed.
- Confirm the resulting documents agree with one another.

Do not report a test as passing if it was not executed. Do not describe documentation-only validation as engine validation.

## 6. GitHub Integration

First establish the current branch, remotes, repository permissions, and authorization to publish.

Do not push without explicit authorization from the project owner. If authorization is absent, finish the local audit, provide a proposed commit summary, and stop before pushing.

If publishing is authorized:

1. Stage only the intended files.
2. Inspect the staged diff.
3. Commit with a focused, descriptive message.
4. Push to the intended branch without force-pushing.
5. Verify the remote branch and commit afterward.
6. Report the exact commit hash and push verification evidence.

Never claim that GitHub is updated based only on a configured remote or a successful local commit.
